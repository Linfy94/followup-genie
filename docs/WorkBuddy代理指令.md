## Agent 的任务

读取业务授权的腾讯文档项目台账，按业务确认的流程节点、超期天数和复提醒规则生成催办清单，
发送到指定的企业微信测试群。台账是业务事实来源，任何情况下都不得修改。

你负责完成目录、配置、检查、试跑、对账和运行；业务只负责回答业务问题并确认结果。

## 不可突破的规则

1. 腾讯文档只读。不得调用任何写表、改单元格、改格式、增删行列或执行表格脚本的能力。
2. 业务明确回复“确认通过”前，只能运行诊断模式，不得真实发送或写状态。
3. 不猜字段、不猜状态、不猜超期规则；缺信息时一次只问一个问题。
4. 不覆盖已有配置、状态或凭证。升级和重复设置都必须保留 `runtime`。
5. 凭证只写到本地 `runtime/.env`，不得复述、打印或放进 Git。
6. 发送不完整或失败时，不得把对应项目记为已经通知。
7. 不要求业务运行命令、编辑 JSON、查日志路径或理解技术术语。

## WorkBuddy 首次接入流程

### 1. 定位运行目录

以当前 WorkBuddy 工作空间为根目录，新建：

```text
runtime/
├── .env
└── followup/
    ├── config/
    └── state/
```

后续调用脚本时始终令 `FOLLOWUP_HOME` 指向这个 `runtime`。

**不要自己挑安装脚本。** 唯一入口是 `python3 scripts/bootstrap.py --host workbuddy --workspace <当前工作空间>`，
它会把代码放到该放的位置，再自动选对下游脚本（WorkBuddy 走 `setup.sh`，Hermes 走 `install.sh`）。
自己直接调 `setup.sh` 或 `install.sh` 会绕过代码分发那一步。

### 2. 初始化配置

把 `templates/*.example.json` 复制到：

```text
runtime/followup/config/holidays.json
runtime/followup/config/ledgers.json
runtime/followup/config/output.json
runtime/followup/config/rules.json
```

目标文件已存在就跳过，绝不覆盖。

演练阶段确保：

- `reminders.write=false`
- `calendar.write=false`
- `wecom_webhook.enabled=false`
- 明确新增 `notify.primary="stdout"`；不能依赖缺省值

正式测试群发送前，才把主通道改为 `wecom_webhook` 并启用。

### 3. 一次只问一个业务问题

按顺序收集：

1. 测试台账链接。
2. 要读取的子表。
3. 稳定唯一的项目编号列。
4. 项目名称列。
5. 哪些项目属于催办范围。
6. 每个流程节点的判断字段和值。
7. 每个节点停留多少天开始催。
8. 每隔多少天重复提醒。
9. 首次计算停滞天数用哪个日期。
10. 哪些值表示终止或暂缓。
11. 腾讯文档本地授权凭证。
12. 企业微信测试群 Webhook。

每得到一项就复述业务含义并让业务确认。示例只能用于解释，不能直接写入正式配置。

### 4. 写入本地配置

- 只修改 `runtime/followup/config/`。
- 凭证只写 `runtime/.env`：

```text
TENCENT_DOCS_TOKEN=业务本人提供的值
FOLLOWUP_WECOM_WEBHOOK=测试群机器人地址
```

- 不显示完整凭证。
- 新业务线只新增配置，不修改 Python 代码。
- 主键必须非空且唯一；项目名称不能当主键。

### 5. 先检查配置

从 Skill 根目录运行：

```bash
FOLLOWUP_HOME="<当前工作空间>/runtime" python3 scripts/doctor.py --validate-config
```

有红色错误就停止，用业务语言说明缺什么。不要自动改业务规则。

### 6. 再做只读试跑

```bash
FOLLOWUP_HOME="<当前工作空间>/runtime" \
python3 scripts/check_followup.py --dry-run --verify-readonly
```

向业务报告：

- 读取的台账和子表。
- 有效项目总数。
- 应催、未超期、终止、暂缓、范围外各多少。
- 至少 5 个项目的编号、节点、起算日期、停滞天数和结论。
- 台账运行前后是否保持不变。
- 所有警告。

然后停止，等待业务明确回复“确认通过”。“看起来可以”“你继续吧”等模糊表达不算通过。

### 7. 通过后做一次测试群发送

确认 `output.json`：

- `notify.primary="wecom_webhook"`
- `wecom_webhook.enabled=true`
- `reminders.write=false`

再执行一次真实运行。报告读取项目数、应催项目数、消息分片数、每片发送结果和通知状态是否提交。
任何一片失败都视为整批失败，不提交 `last_notified`。

### 8. 引导业务创建自动化

在 WorkBuddy 自动化中使用当前工作空间和本 Skill，先设为工作日每天一次。自动化提示词固定为：

> 调用项目跟进精灵，使用当前工作空间的 `runtime`。先检查配置，再执行当天正式催办。
> 腾讯文档只读；失败或发送不完整时不得提交通知状态。最终明确报告是否启动、读取项目数、
> 应催项目数、发送是否完整、状态是否提交。

创建后立即手动触发一次，确认无人值守时不会被权限弹窗卡住；连续观察 3 个工作日后再扩大使用。

## 日常请求怎么处理

| 业务说法 | Agent 动作 |
|---|---|
| 今天有什么要催的 | 执行当天检查，转述脚本结果，不自行复算 |
| 为什么某项目没被催 | 用 `--json` 查看它属于未超期、终止、暂缓、范围外还是复提醒间隔 |
| 只检查一下 | 使用 `--dry-run`，不发不写 |
| 接另一张台账 | 重走首次接入流程，只新增配置 |
| 修改超期天数 | 先复述变更影响，得到确认后改 `rules.json`，再检查和试跑 |

项目推进、终止或暂缓后，应由业务正常更新台账。删除消息或勾选提醒事项不会停止催办。

## 出错时

- 没有任何反应：查看 WorkBuddy 任务历史，确认客户端在线、电脑未休眠，并记录准确时间。
- 显示成功但群没消息：先确认应催数是否为 0，再检查是否仍为演练模式和每片发送结果。
- 项目结果不对：报告项目编号、台账节点、工具节点、起算日期和停滞天数；不擅自改规则。
- 配置或状态损坏：停止扩大使用，保留损坏文件和日志，不删除状态“重试”。
- WorkBuddy 要求无关目录、删除、写腾讯文档或完全访问：拒绝并停止。

## 当前边界

- WorkBuddy 客户端的包导入、无人值守权限、休眠补跑和升级保留状态仍需实机验证。
- Windows 尚未验证。
- 独立看门狗已交付（`scripts/watchdog.py`，装在运行时目录、与 Skill 解耦），
  但**要人实际装上 launchd 并跑过一次 `--self-test` 才算闭环**。没装之前，
  电脑休眠或定时任务未启动时，主任务自身仍无法告警。
- 当前只支持腾讯文档台账，不包含微信聊天记录自动更新台账。
