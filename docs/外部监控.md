# 外部存活监控

> 🛑 **本文档描述的东西已经交付，但默认没有安装。**
> 在你实际执行下面的安装步骤之前，「能发现任务根本没跑」**只是能力，不是闭环**。

## 它解决什么

主脚本能报取数失败、推送失败、状态损坏——**但它得先跑起来才能报。**

有一类失败连一行报错都不会产生：

- 电脑关机或休眠过了触发时刻
- Hermes 的 gateway 没起来
- 定时任务被误删或被禁用
- 整个 skill 目录被移动/删除

这几种情况没有进程、没有日志、没有异常。业务只会觉得「最近很安静」，
**而那和「最近确实没有要催的」长得一模一样。**

`doctor` 查得到（它看 `health.json` 里的 `last_full_success`），但 `doctor` 要人手动跑。
而把检查挂进 `hermes cron` 又是循环依赖——gateway 没起来时，
「检查 gateway 起没起来」的那个任务同样不会执行。

所以执行者必须在 Hermes 之外：**launchd**。

```
launchd（macOS 自带，与 Hermes 无关）
   └─ 每天 10:30 / 15:30 + 开机时，跑 /usr/bin/python3 watchdog.py
        └─ 读 followup/state/health.json
             └─ 连续错过应跑 → 告警
```

## 判定口径：数班次，不数小时

**小时阈值在这台机器上是错的工具。** 作息是「工作日不关机，周末可能关机」：

- 设 48 小时 → 周四的故障能潜伏到周末
- 设 60 小时 → 周一早上必误报（周五跑完 → 周末关机 → 周一开机补跑，
  中间隔了 72 小时，却**一次都没缺勤**）

改成数「错过了几次本该执行的 9:00」，并跳过周末，两种情况都对：

| 场景 | 错过班次 | 告警？ |
|---|---|---|
| 周五成功 → 周末关机 → 周一 9:00 补跑成功 → 周一 10:30 检查 | 0 | ❌ 不报 ✅ |
| 周五成功 → 周一开机但 gateway 挂了 → 周一 10:30 | 1 | ❌ 不报（容一次抖动） |
| 同上 → 周二 10:30 | 2 | ✅ **报** |
| 周三成功 → 周四挂 → 周五 10:30 | 2 | ✅ **报** |

另有两条兜底：

- `health.json` **不存在**：给 36 小时宽限（刚装完还没跑过属正常），之后报
- **绝对上限 7 天**：防止班次逻辑本身被配错把告警吃掉

## 告警通道：为什么是这条

四条路都评估过：

| 通道 | 独立性 | 可靠性 | 迁到业务机后 | 评价 |
|---|---|---|---|---|
| **`hermes send`** | 中 —— **不需要 gateway 在跑**（bot-token 平台直连各自的 REST 接口，已核实），但依赖 hermes 装还在 | 高 | 需要她那台配好 telegram | ⭐ **选它做主路** |
| **macOS 本机通知** | 最高 —— 零网络、零凭证、零依赖 | 低 —— 人不在电脑前就看不到，通知中心也不留可靠历史 | 一样能用 | ⭐ **选它做兜底** |
| 自己直连 Telegram Bot API | 最高 | 中 —— 本机要靠系统代理（`127.0.0.1:7890`）才通 | 🔴 **业务那台没 VPN，必挂** | 否决 |
| 只写日志 | 最高 | 最低 —— 没人会主动看日志 | — | 只当第三级 |

**最终：`hermes send` → 失败退到本机通知 → 再失败写日志并非零退出。**

不选「自己直连 Telegram」的原因不是技术上做不到，而是：要在监控器里重造一遍
代理处理和 bot token 解析，**而这份重复在业务那台没有 VPN 的机器上直接作废**。
`hermes send` 是已经在用、已经验证过的那条路。

⚠️ **「任务根本没跑」这类故障，恰恰常发生在你没在用这台机器的时候。**
所以只靠本机通知是不够的——那正是主路要能发到手机上的原因。

## 安装（需要你自己执行）

```bash
SKILL=~/.hermes/skills/work/followup-genie

# 1. 复制模板
cp $SKILL/templates/com.linfangyu.followup-watchdog.plist.example \
   ~/Library/LaunchAgents/com.linfangyu.followup-watchdog.plist

# 2. 编辑里面的三处 <请改成…>，换成真实绝对路径
open -e ~/Library/LaunchAgents/com.linfangyu.followup-watchdog.plist

# 3. 装载
launchctl load -w ~/Library/LaunchAgents/com.linfangyu.followup-watchdog.plist

# 4. 确认它在
launchctl list | grep followup-watchdog
```

### 装完必须验一次告警链路

```bash
FOLLOWUP_HOME=~/.hermes python3 $SKILL/scripts/watchdog.py --self-test
```

⚠️ **这会真发一条测试消息。** 收到了才算通。

**没验过就等于没装**——监控器最怕的失败模式就是「它一直在跑，但出事时告警发不出去」，
而那件事只有真发一次才知道。

### 先看看它现在怎么判

```bash
FOLLOWUP_HOME=~/.hermes python3 $SKILL/scripts/watchdog.py --dry-run
```

不发不写，只打印判定结果。

## 卸载

```bash
launchctl unload -w ~/Library/LaunchAgents/com.linfangyu.followup-watchdog.plist
rm ~/Library/LaunchAgents/com.linfangyu.followup-watchdog.plist
```

状态文件 `followup/state/watchdog_state.json` 和 `watchdog.log` 不会被删，可自行清理。

## 配置

在 `followup/config/output.json` 的 `watchdog` 段：

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 关掉它监控器就直接退出 |
| `schedule_hour` | `9` | 主任务本该在几点跑 |
| `count_weekends` | `false` | 周末的那一班算不算「本该跑」。**这只影响告警判定，不改 cron 的推送时刻** |
| `missed_runs_before_alert` | `2` | 错过几次才报。设 1 会因一次网络抖动就吵 |
| `absolute_max_hours` | `168` | 兜底上限（7 天） |
| `repeat_alert_hours` | `24` | 同一故障多久内不重复告警 |
| `missing_health_grace_hours` | `36` | 还没有健康记录时的宽限 |

## 四类消息，别混

| 类别 | 去哪 | 何时 | 无事发生时 |
|---|---|---|---|
| **企微业务消息** | 业务群 | 有待催项目 | **不发**（无事不发） |
| **本地运行回执** | stdout → 宿主日志 | **每次真实运行** | 仍打一行摘要 |
| **故障告警** | telegram | 取数/推送/状态损坏/配置故障 | 不发 |
| **外部存活监控** | telegram + 本机通知 | 连续错过应跑班次 | 不发 |

前三类都需要**任务跑起来**才会产生。第四类是唯一在任务压根没跑时还能出声的。
