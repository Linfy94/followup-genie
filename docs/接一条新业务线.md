# 接一条新业务线

从「拿到台账链接」到「跑通第一次催办」。**只加配置，不改代码。**

预计 1–2 小时，其中一半时间花在跟业务对规则口径上——那部分省不掉，也不该省。

---

## 第 0 步：先问一个问题，别急着写配置

**「这个业务线里，卡住的项目是因为负责人忘了催，还是因为在等外部条件？」**

这个问题决定这条线值不值得接。如果答案基本都是「等客户/等厂家/等物料」，那催办解决不了问题，应该做的是**阻塞归类**（等谁的各多少条），不是催办。

验证方法：先手工跑一遍（见第 4 步），把结果给业务看，问「**这里面有几条是你原本不知道的？**」

- 接近 0 → 这条线不适合做催办
- 显著大于 0 → 继续

---

## 第 1 步：判断台账的表结构类型

打开台账，看它怎么记录进度。常见两种：

| 类型 | 长什么样 | 好不好接 |
|---|---|---|
| **状态列型** | 一列「当前状态」，值在几个词之间流转 | 好接。需要业务给出**完整的状态枚举** |
| **多时间列型** | 每个节点一列，做完了就填内容/日期 | **更好接**。当前节点 = 最后一个有值的节点的下一个 |

**登记册类台账多为多时间列型，也更可靠**——它天然记录了"做到哪一步"。

⚠️ 如果是状态列型，**必须先拿到状态枚举**。这不是可以边做边补的东西：多数节点的停催条件就是「状态变成某个值」，枚举拿不到，项目做不了。

## 第 2 步：实际读一次，看清真实结构

别信别人转述的字段名，自己读一次。

**先确认台账在哪个平台**——两条通道都已实现，配置字段不同：

| 台账在 | `source` | 关键字段 | 需要装什么 |
|---|---|---|---|
| 腾讯文档 | `tencent_mcp` | `file_id` + `sheet_id` | 什么都不用装，只要 `.env` 里的 `TENCENT_DOCS_TOKEN` |
| 飞书多维表格 | `lark_cli` | `base_token` + `table_id` + `profile` | Node.js + `lark-cli`；完整执行 `飞书多维表格接入.md`，确保配置、登录与读取使用同一个 profile。**不需要腾讯文档凭证** |

一份配置里两种混用是正常的，只用一种时另一种的凭证不必配，自检也不会要求你配。
下面的读表示例是腾讯文档；飞书换成 `lark_base.read_sheet(base_token, table_id, profile=...)`，
返回的对象接口完全一样（`header` / `data_rows` / `text` / `date` / `has_column`）。

```bash
cd <程序目录>/scripts
python3 - <<'PY'
import qqdoc, collections
FILE_ID = "从链接里取"      # docs.qq.com/sheet/【这一段】
# 先看有哪些子表
info = qqdoc.call_tool("sheet.get_sheet_info", {"file_id": FILE_ID})
for s in info["sheets"]:
    print(s["sheet_id"], s["sheet_name"], s["row_count"], "行", s["col_count"], "列")
PY
```

拿到 `sheet_id` 后读结构：

```bash
python3 - <<'PY'
import qqdoc, collections
sheet = qqdoc.read_sheet("FILE_ID", "SHEET_ID")
print("表头：", [h for h in sheet.header if h])
rows = [r for r in sheet.data_rows if sheet.text(r, "项目名称")]   # 换成实际的名称列
print(f"{len(rows)} 个有效项目")
for col in [h for h in sheet.header if h]:
    vals = collections.Counter(sheet.text(r, col) for r in rows)
    blank = vals.pop("", 0)
    top = dict(list(vals.most_common(6)))
    print(f"  {col}: 空{blank}/{len(rows)}  {top}")
PY
```

**要从输出里确认四件事**：

1. **主键列**：哪一列是稳定唯一的标识（序号这类）。不要用项目名称——名字会被改写、会带后缀
2. **日期列**：有哪些、空值率多少
3. **节点列的真实取值**：别假设只有「完成」，实测常混入「已完成」「完成✓」这类写法
4. **节点的真实顺序**：如果不确定，看填写组合——如果 A 有值时 B 必有值，说明 B 在 A 之前

> 顺序判断错了，规则会永不触发或永远触发。盒子那条线上我判断错了两次，都是靠填写组合的嵌套关系才纠正过来的。

## 第 3 步：写配置

```bash
cp templates/ledgers.example.json <运行时目录>/followup/config/  # 若已有则手工合并
cp templates/rules.example.json   <运行时目录>/followup/config/
```

两个模板里的 `_xxx说明` 字段有详细注释，照着填。几个容易错的点：

**`required_columns`** —— 把规则用到的列全列进去。这是入口断言，缺列会直接报错拒跑，而不是静默跑出「今天没有超时单」。

**`clock`（计时起点）** —— 两种写法，选错了结果会离谱：

- 规则说「**自上报日起** N 天」→ `{"field": "上报日期列"}`
- 规则说「**XX完成后** N 天」→ `{"stage_entered": true, "fallback": "最新进展日期"}`

  🔴 `fallback` 必填。首次运行没有快照，靠它兜住。**如果起点初始化成「今天」，已经停滞几个月的存量项目会被算成停滞 0 天，首次运行一条都不催，而且不报错。**

**`repeat`（复提醒间隔）** —— 每个启用的节点都必须有，缺失会报错。**不允许出现「只催一次然后永久静默」的节点**，那会让项目悄悄沉没，而这恰恰是本工具要解决的问题。

**`scope_filters`** —— 留空 = 全量。绝不为了"先跑起来"随手收窄，静默漏催比多催难发现得多。

## 第 4 步：验证

```bash
python3 scripts/doctor.py --validate-config   # 先查配置，不联网
python3 scripts/doctor.py                     # 全项自检，含只读性验证
python3 scripts/check_followup.py --dry-run   # 试跑，不写状态
```

**必须核对的四件事**：

1. **各项之和 = 项目总数**。报告里会算这个，对不上会警告「有行去向不明」
2. **随机抽 3 条到台账里人工核对**：这个项目确实卡在这个节点、确实超了这么多天。对不上就是配置错了，不要圆过去
3. **看「⏸ 未启用」的节点列表**：确认那些是你有意禁用的
4. **看「⚠️」警告**：特别是「出现未知取值」——那说明写法不统一，会被静默丢掉

然后做降噪回归（这是催办类产品的生死线）：

```bash
# 用隔离目录测，不污染真实状态
SB=$(mktemp -d); mkdir -p "$SB/followup/state"
cp -R <运行时目录>/followup/config "${SB}/followup/config"; cp <运行时目录>/.env "${SB}/.env"

FOLLOWUP_HOME="${SB}" python3 scripts/check_followup.py --today 2026-08-01  # 首次，应有条目
FOLLOWUP_HOME="${SB}" python3 scripts/check_followup.py --today 2026-08-01  # 同天，应静默
FOLLOWUP_HOME="${SB}" python3 scripts/check_followup.py --today 2026-08-08  # 满间隔，应重新催
```

## 第 5 步：跑起来

确认试跑无误后：

```bash
hermes cron create "0 9 * * *" --name "项目跟进精灵" --script followup_genie.py --no-agent
```

`--no-agent` 是纯规则模式，零 LLM 零 token。**先让它在演练模式下跑两周**（`reminders.write=false`），人工核对每天的输出，再打开真实写入。

**催办类产品第一印象很难挽回**，宁可多跑两周空转。

## 常见坑（都是实测踩过的）

| 现象 | 原因 |
|---|---|
| 主键读到空、例外表全失效但总数看着正常 | 主键列是数字类型。取值必须先看 `value_type`——这个坑已在 `qqdoc.cell_text()` 里封好，别绕过它自己读 |
| 数据整体错位一格、字段对不上 | 行列索引从 0 开始，`end` 是包含式。已在 `qqdoc.read_sheet()` 里封好 |
| 业务加了一列之后全乱 | 按位置读列了。**一律按列名读**，`Sheet` 类只提供按名字的接口 |
| 日期解析失败 | 用了 CSV 模式。CSV 返回的是按显示格式渲染的字符串，业务改一次格式就挂。用 cells 模式读 serial number |
| 某个节点永不触发 | 节点顺序判断错了，或者它的 `when` 条件被前面的节点抢先匹配了。当前节点 = 从上往下第一个满足的 |
| 「今天没有超时单」但其实是故障 | 凭证过期、网络不通、字段改名。这三种都会伪装成正常。`doctor.py` 专门查这些，**定期跑** |
| 台账里的统计列（已停滞天数之类）和自己算的不一致 | 那些列多半是手填的静态值，滞后。一律自己从日期算 |

## 别做的事

- **不要为了实现某个功能而回写台账。** 砍功能，不破例
- **不要把配置或状态放进 skill 目录。** 一次 `hermes skills update` 就冲掉了
- **不要给节点默认一个复提醒间隔。** 缺失就报错，让人显式填
- **不要在模板里留真实的企业名、业务专有字段名。** 模板是给别的业务线用的
