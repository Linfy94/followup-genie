# 项目跟进精灵业务操作手册

零基础版｜适用于 WorkBuddy 业务试用  
版本：`0.4.0-rc10`｜状态：预发布内测

---

## 先看结论

使用这个工具不需要懂 Git、代码或命令行。业务只做三件事：

1. 把根目录 README 顶部唯一的一段指令发给当前 Agent。
2. 根据提示提供测试台账和业务规则。
3. 核对催办清单是否正确。

遇到报错不要自己改代码。保存截图、发生时间和测试项目名称，交给项目维护人员处理。

## 一页式快速开始

### 开始前向项目负责人领取

- README 顶部的唯一业务指令。
- 一张测试台账，优先使用真实台账的副本。
- 一个只用于测试的企业微信群。
- 腾讯文档授权方式和测试群机器人地址。

### 安装

在当前 Agent 中发送 README 顶部的唯一业务指令。Agent 会下载、校验并安装到当前工作空间。
这种方式以“当前工作空间可以立即运行”为成功标准，不承诺显示在 WorkBuddy 的技能列表。
如确实需要显示在技能列表，再手动上传同一 Release 中的 `followup-genie-workbuddy.skill`。

### 第一次设置

在 WorkBuddy 新建一个独立工作空间，名称建议为“项目跟进精灵测试”，然后发送 README
顶部的唯一业务指令。安装完成后继续在同一任务里回答 Agent 的问题。

### 第一次验收

配置完成后不需要复制第二条指令。Agent 必须先做配置检查和只读试跑，并等待业务明确
回复“确认通过”。

确认结果正确后，才进入测试群投递和自动化。

# 1. 这是什么

项目跟进精灵会读取项目台账，根据流程节点和超期规则，找出“现在需要业务催一下”的项目。

它能做：

- 找出卡住的项目。
- 计算停滞天数。
- 按业务线和节点生成催办清单。
- 把清单发送到指定的企业微信测试群。
- 回答“为什么这个项目没有被催”。

它不能做：

- 不会修改、补写或删除腾讯文档台账。
- 不会自动从微信聊天记录更新项目进展。
- 不会替业务判断客户是否真的终止项目。
- 不会把提醒事项的勾选结果写回台账。

台账是唯一业务事实来源。项目推进、终止或暂缓后，应由业务正常更新台账。

# 2. 谁负责什么

| 角色 | 负责内容 | 不需要做 |
|---|---|---|
| 业务使用人员 | 发送唯一指令、提供规则、核对结果、日常看清单 | 不改代码、不操作 GitHub |
| 业务负责人 | 确认节点、超期天数、终止和暂缓口径 | 不处理技术报错 |
| 项目维护人员 | 打包、升级、修复问题、协助查日志 | 不替业务决定规则 |

如果 WorkBuddy 问到业务不确定的字段或规则，选择“暂不配置”，再找业务负责人确认。

# 3. 安装到 WorkBuddy 当前工作空间

## 3.1 发送唯一指令

把 README 顶部的完整段落发给当前 Agent。成功标准：

- Agent 报告版本为 `0.4.0-rc10`。
- 程序目录位于当前工作空间的 `.followup-genie`。
- 运行目录位于当前工作空间的 `runtime`。
- 离线配置检查通过。

这条路径不以“技能列表可搜索到”为成功标准。需要进入技能列表时，手动上传同一版本
的 `followup-genie-workbuddy.skill`。

## 3.2 权限提示怎么选

建议保持 WorkBuddy 的“默认权限”。

首次运行时可能出现以下确认：

| WorkBuddy 提示 | 怎么处理 |
|---|---|
| 在当前工作空间新建文件 | 可以允许 |
| 运行项目跟进精灵脚本 | 可以允许 |
| 访问腾讯文档或企业微信网络地址 | 核对地址后允许 |
| 修改腾讯文档 | 拒绝，并停止测试 |
| 删除文件或访问无关文件夹 | 拒绝，并截图反馈 |
| 访问整个桌面、下载目录或个人主目录 | 拒绝，改用独立测试工作空间 |

不确定时不要点“完全访问”，先截图给项目维护人员。

# 4. 准备测试资料

## 4.1 测试台账

优先使用真实台账的副本。不要第一次测试就连接唯一的生产台账。

业务需要知道：

- 哪一列是项目编号。
- 哪一列是项目名称。
- 哪些列表示流程节点。
- 哪一列是需求上报日期或最新进展日期。
- 哪些状态表示终止、暂缓或不在催办范围。

## 4.2 业务规则

请业务负责人填写：

| 问题 | 示例 | 业务填写 |
|---|---|---|
| 业务线叫什么 | 节能项目 |  |
| 第一个节点是什么 | 待收资 |  |
| 停留几天开始催 | 满 7 天 |  |
| 多久重复提醒 | 每 7 天 |  |
| 什么表示终止 | “终止”“不推进” |  |
| 什么表示暂缓 | “暂缓” |  |
| 清单发到哪里 | 企业微信测试群 |  |

示例只能帮助理解，不能直接当成业务答案。

## 4.3 凭证

腾讯文档凭证和企业微信机器人地址相当于钥匙：

- 只填写在业务电脑的本地运行目录。
- 不发到微信群、邮件或问题单。
- 截图时遮住完整内容。
- 不上传到 GitHub 或网盘共享目录。

业务不会配置时，联系项目维护人员现场协助，不要把完整凭证发给对方。

# 5. 配置与只读演练

## 5.1 让 WorkBuddy 带着完成配置

复制：

> 请调用项目跟进精灵，在当前独立工作空间中完成一张新腾讯文档项目台账的配置。
> 请一次只问我一个业务问题，并用例子解释。不要猜字段、状态或规则，不要覆盖已有配置。
> 配置完成后只检查配置，不发送消息，不写提醒事项，不修改台账。

WorkBuddy 会逐项提问。业务只需回答自己确定的内容；不确定就说“需要业务负责人确认”。

## 5.2 只读演练

复制：

> 请进行只读试跑。禁止发送企业微信，禁止写提醒事项，禁止修改腾讯文档。
> 请列出应催项目，并同时告诉我：总项目数、未超期数、终止数、暂缓数、范围外数量和警告。

成功标准：

- 没有红色错误。
- 能看到读取的台账名称和项目数量。
- 每个项目都有明确去向。
- 腾讯文档内容和最后修改时间没有因为试跑发生变化。

## 5.3 人工抽查

从结果中至少抽 5 个项目：

- 3 个普通项目。
- 1 个终止项目。
- 1 个暂缓项目。

逐个核对项目名称、当前节点、起算日期、停滞天数和是否应该催办。对不上就停止测试，
不要用“可能差不多”放过。

# 6. 测试群投递与自动化

## 6.1 第一次真实发送

先确认企业微信只连接到测试群，然后复制：

> 请先检查配置；通过后执行一次正式催办，只发送到测试群。
> 请报告读取项目数、应催项目数、发送了几段、每段是否成功、通知状态是否提交。
> 任何发送失败都不得把这批项目记为已经通知。

成功标准：测试群收到的项目数量、顺序和本地结果一致。

## 6.2 创建自动化

在 WorkBuddy 的“自动化”页面新增任务：

- 名称：项目跟进精灵每日检查。
- 工作空间：项目跟进精灵测试。
- 技能：项目跟进精灵。
- 频率：先设为工作日每天一次。
- 推送：先按业务测试要求选择。

自动化提示词：

> 调用项目跟进精灵，使用当前工作空间的 `runtime` 运行目录。先检查配置，再执行当天催办。
> 腾讯文档只读；只向配置中的测试群发送；失败时不得提交通知状态。
> 最终明确报告：是否启动、读取项目数、应催项目数、发送是否完整、状态是否提交。

创建后立即手动触发一次。确认没有新的权限弹窗卡住，再观察连续 3 个工作日。

提示：WorkBuddy 自动化会发起 Agent 任务，可能消耗积分；电脑休眠、WorkBuddy 退出或网络中断
时是否补跑，需要以业务电脑实测为准。

# 7. 日常怎么用

## 7.1 正常情况

自动化启用后，业务每天只需要：

1. 查看企业微信或 WorkBuddy 的当天结果。
2. 按清单联系相关人员。
3. 项目推进、终止或暂缓后，正常更新腾讯文档台账。

台账不更新，项目跟进精灵就会继续认为项目停在原节点。这是设计规则，不是故障。

## 7.2 常用提问

直接对 WorkBuddy 说：

- “今天有什么要催的？”
- “为什么某某项目今天没有被催？”
- “只读试跑一次，不要发送消息。”
- “检查配置，但不要修改。”
- “某条业务线现在卡在哪些节点？”
- “列出超过两个月还没有推进的项目。”

## 7.3 怎么停止某个项目的催办

正确做法：在腾讯文档中把项目更新到下一节点，或按业务规则标记为终止、暂缓。

错误做法：

- 只删除企业微信消息。
- 只勾选 macOS 提醒事项。
- 要求 WorkBuddy 把项目从本地结果中永久隐藏。

# 8. 接入另一张项目台账

不要复制旧台账配置后直接改几个名字。先复制：

> 请调用项目跟进精灵，为另一张腾讯文档项目台账做接入评估。
> 请逐项询问业务线名称、稳定项目编号、项目名称列、范围、节点、阈值、重复提醒、
> 起算日期、终止与暂缓信号、测试群。不要猜，不要改代码，不要覆盖现有业务线。
> 完成后只做配置检查和只读演练。

新台账必须重新完成 5 个项目抽查和测试群投递，不因为旧业务线已经通过就跳过。

# 9. 常见问题

## 9.1 上传 `.skill` 失败

1. 确认文件已完整下载。
2. 改用同版本 `.zip` 文件。
3. 仍失败就记录 WorkBuddy 版本、电脑系统和错误截图。
4. 不要连续卸载、重装或改压缩包内容。

## 9.2 手动触发后没有任何反应

1. 等待 2 分钟，避免重复触发。
2. 打开 WorkBuddy 自动化历史，查看任务是“未启动、运行中、失败”还是“成功”。
3. 确认 WorkBuddy 正在运行、电脑没有休眠、网络正常。
4. 在普通对话中发送：“只做配置检查，不发送消息。”
5. 仍无反应时记录准确时间并截图。
6. 在 WorkBuddy“帮助”中打开日志文件夹，把对应时间的日志压缩包交给项目维护人员。

日志可能包含对话和设备信息，发送前先确认接收人并按公司要求脱敏。

## 9.3 WorkBuddy 显示成功，但企业微信群没有消息

先看结果里“应催项目数”：

- 如果是 0：当天可能确实没有需要催办的项目，但仍应有明确的“0 个”结果。
- 如果大于 0：检查是否仍处于只读演练、测试群机器人是否启用、发送结果是否完整。

不要因为没看到群消息就反复正式触发，可能造成重复消息。

## 9.4 某个项目算错了

不要先改规则。记录：

- 项目编号和项目名称。
- 台账当前节点。
- 业务认为的起算日期和停滞天数。
- 工具显示的节点和停滞天数。
- 发生日期和结果截图。

项目维护人员应根据这些信息复现，而不是让业务提供完整台账或凭证。

## 9.5 想升级新版本

1. 先暂停自动化。
2. 保留当前独立工作空间和其中的 `runtime` 目录。
3. 上传项目维护人员提供的新版本安装包。
4. 先运行配置检查和只读试跑。
5. 对比升级前后结果，再恢复自动化。

不要删除 `runtime/config` 和 `runtime/state`。它们保存业务配置和已经积累的节点计时。

# 10. 安全红线

- 不允许项目跟进精灵修改腾讯文档。
- 不把 token、Webhook、真实配置或客户名单上传到 GitHub。
- 不在群聊中发送完整凭证。
- 不给 WorkBuddy 整个电脑的完全访问权限。
- 不直接在生产群做第一次发送。
- 不在结果不一致时继续扩大使用范围。
- 不删除运行状态来“解决”没有反应的问题。
