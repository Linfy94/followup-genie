# 改一个催办节点

> 接一整份新台账看 [接一条新业务线.md](接一条新业务线.md)。
> 这一份只管**已经在跑的节点**要改的时候怎么改。

## 先说三件事

**① 催办节点是配置，不是代码。** 开关、触发条件、多久算超期、多久提醒一次、
显示的文案，全在 `<运行时目录>/followup/config/rules.json` 的
`rulesets.<台账id>.nodes[]` 里。

**② 改完不用发版、不用部署、不用重启。** 配置只有一份，程序每次运行都重新读它。
今天改，明天 9:00 那次就按新的来。

**③ 唯一的风险是「改错了但不报错」。** 这类写法能过 JSON 语法、能过离线校验、
运行时也不抛错，只是让那个节点从此不再产生催办 —— 一条日志都没有，
业务只是再也收不到那条提醒。下面每一条流程里的校验步骤都是为它准备的。

## 三条命令，改什么都用它们

```bash
cd ~/.hermes/skills/work/followup-genie
```

| 命令 | 干什么 | 什么时候用 |
|---|---|---|
| `FOLLOWUP_HOME=~/.hermes python3 scripts/doctor.py --values <台账id>` | 只读列出这份台账里判据用到的每一列的**真实取值** | 改触发条件**之前** |
| `FOLLOWUP_HOME=~/.hermes python3 scripts/doctor.py --validate-config` | 离线查配置，不联网 | 改完立刻 |
| `python3 scripts/diff_due.py 改前.json 改后.json` | 待催名单逐条比对 | 改完，提交之前 |

名单快照这样存（**严格只读**，不发消息、不写状态）：

```bash
FOLLOWUP_HOME=~/.hermes python3 scripts/check_followup.py --dry-run --json > /tmp/before.json
```

## 情形一：改参数（天数、节律、开关、文案）

最常见，也最安全 —— 纯离线可验证。

```bash
# 1. 存改前的名单
FOLLOWUP_HOME=~/.hermes python3 scripts/check_followup.py --dry-run --json > /tmp/before.json

# 2. 改 ~/.hermes/followup/config/rules.json

# 3. 离线校验
FOLLOWUP_HOME=~/.hermes python3 scripts/doctor.py --validate-config

# 4. 存改后的名单并比对
FOLLOWUP_HOME=~/.hermes python3 scripts/check_followup.py --dry-run --json > /tmp/after.json
python3 scripts/diff_due.py /tmp/before.json /tmp/after.json

# 5. 差异符合预期就提交
cd ~/.hermes/followup/config && git add -A && git commit
```

能改的字段：

| 字段 | 意思 | 注意 |
|---|---|---|
| `enabled` | 开不开 | **必须是 `true` / `false`，不带引号**。字符串 `"false"` 在程序里是**真**，会把节点静默开着 |
| `threshold.days` | 在这个节点待满几天算超期 | 数的是**自然日**，含节假日 |
| `threshold.workdays` | 同上，但只数工作日 | 与 `days` 二选一 |
| `threshold.boundary` | `on` = 满 N 天当天就提醒；`after` = 第 N+1 天 | 🔴 **全线统一为 `on`**（2026-08-14 业务确认），配置里已无 `after`。**新增节点必须显式写** —— 代码缺省仍是 `after`，忘填会静默回到旧口径、首次提醒晚一天，而且不报错 |
| `repeat` | 多久提醒一次 | 四选一，见下 |
| `name` / `stage` / `action` / `backlog_note` | 给业务看的文案 | 不影响判定 |

`repeat` 四种写法，**只能配一种**：

```jsonc
{"days": 7}                    // 每 7 个自然日
{"workdays": 2}                // 每 2 个工作日
{"weekday": ["Mon", "Thu"]}    // 每周一和周四
{"monthday": [1, 15]}          // 每月 1 号和 15 号
```

🔴 **`days` / `workdays` 必须是 ≥1 的整数。** 小数会被悄悄截断，
负数会让「距上次提醒 ≥ -3 天」恒成立 —— 节律静默变成每天提醒，
而配置看起来是配过的。离线校验现在会拦，但别去试。

🔴 **业务说的「隔周」＝每周一次、7 天**（2026-08-10 她本人确认），
「隔天」＝每天。别按字面理解成两周。

### 节假日怎么处理（已经是这样，不用配）

- 每天提醒的节点：法定假日、普通周末**不发**，调休补班日**照发**
- 每 7 天提醒的节点：到期日落在假期里，**假期后第一个工作日立刻补上**，
  不是再等一整轮

原理是「假期当天不投递，也就不记『已通知』」，所以假期一过天数早就够了。

## 情形二：改触发条件（换字段、换状态取值）

🔴 **先枚举真实取值，再动手。** 照着业务口头说的写，会一条都匹配不上。

```bash
FOLLOWUP_HOME=~/.hermes python3 scripts/doctor.py --values geo_wecom
```

实测踩过两次：同一个文件里三个子表，分行写成「杭州」和「杭州分行」两种；
GEO 的「启动优化时间」全表 43 种写法，业务说的「未开始」在表里根本不存在
（实际是「未开始，等客户确认平台」等 7 种）。

条件长这样，一个节点的 `when` 里所有条件**同时满足**才算命中：

```jsonc
"when": [
  {"field": "技术确认", "op": "in", "values": ["可行", "有条件可行"]},
  {"field": "安装调试", "op": "empty"}
]
```

八种 `op`，各自要带什么：

| op | 要带 | 意思 |
|---|---|---|
| `in` / `not_in` | `values`（**非空数组**） | 取值在/不在这几个里 |
| `equals` / `not_equals` | `value` | 全等/不等 |
| `contains` / `not_contains` | `value` | 包含/不包含这个子串 |
| `empty` / `not_empty` | 不带 | 这一列空/非空 |

🔴 **漏写取值字段是不报错的，后果是节点静默失效：**

| 写法 | 后果 |
|---|---|
| `{"op": "in"}` 漏 `values` | `取值 in []` **恒假** → 这个节点一条都不催 |
| `{"op": "contains"}` 漏 `value` | `"" in 取值` **恒真** → 这个节点吞掉所有项目，后面的节点全部轮空 |
| 条件漏 `field` | 取值恒为空串，判据静默失效 |

这三种现在都会被 `--validate-config` 拦下来，但要知道为什么拦。

改完照情形一的第 3~5 步走一遍。**因为动了判定，名单出现差异是正常的 ——
要核的是「差异是不是正好是你预期的那些」。**

## 情形三：新增或删除节点

### 🔴 节点顺序有语义

判定取「**第一个** `when` 全部满足的启用节点」就停下。所以：

- 新节点插在数组的哪个位置，决定它和相邻节点谁先命中
- 插在一个条件更宽的节点**后面**，它可能永远轮不到 —— **而且不报错**

新增节点后一定要用 `diff_due.py` 看：有没有一批项目从原来的节点跑到了新节点上。

### 停用不要删

按铁律④「不删除文件，只新增；修改留痕」，停用一个节点是把 `enabled` 改成
`false`，**不是把它从数组里删掉**。运行报告里会打出

```
⏸ ①收资：未启用，不会产生催办
```

—— 明说不催，不是悄悄消失。业务哪天说「文档漏写了」，改回 `true` 就行。

### 新增节点的清单

1. `--values` 确认判据用的列在台账里**真的存在**，取值写法**照抄实测结果**
2. 想清楚它排在数组的第几位
3. `enabled`、`when`、`clock`、`threshold`、`repeat` 五样齐全
   （启用的节点少 `repeat` 会被离线校验拦下 —— 不许有「只催一次」的节点）
4. `--validate-config` → `diff_due.py` → 提交

## 需求文档变了怎么办

程序每天会核一次需求文档有没有被改过。变了就在当天的推送里出现：

```
📌 需求文档《跟进精灵🧚需求文档》被「某某」改过了（时间，上次核对时是 时间）。
   催办规则可能要跟着改 —— 核对完跑一次 `check_followup.py --ack-spec` 消除这条提示。
```

**它只回答「变没变」，不回答「变了什么」。** 变了什么要人自己去读。
好处是：**没出现这条提示的日子，那份文档就不用打开看了。**

核对完（不管最后改没改规则）：

```bash
cd ~/.hermes/skills/work/followup-genie
FOLLOWUP_HOME=~/.hermes python3 scripts/check_followup.py --ack-spec
```

🔴 **提示会一直出现到你跑这条命令为止**，不是只响一天 —— 只响一天等于
「那天没看到就永久错过」。

要盯的文档配在 `rules.json` 顶层：

```jsonc
"spec_watch": [
  {"file_id": "腾讯文档链接 docs.qq.com/doc/<这一段>", "name": "跟进精灵🧚需求文档"}
]
```

## 什么时候不该自己改，先问

- 要改的是**判定优先级阶梯**（哪一层说了算终止）
- 要改**责任范围**（`scope_filters`）—— 它错一次能把整张台账静默过滤光
- 台账里出现了 `known_values` 没列过的新状态值（运行报告会告警）
- 改完 `diff_due.py` 出来的差异**和你预期的不一样** —— 停下来查清楚再提交，
  别先提交再说

## 一条铁律

**台账永远只读。** 不管改什么节点，程序都不会往台账里写一个字。
「把已催办标记写回台账」这种需求不允许实现 —— 台账是业务的生产数据，
程序误写一次，她就再也分不清哪些是人改的。
