# 飞书多维表格接入（从零安装）

本页只解决一件事：让项目跟进精灵以**业务本人**的飞书身份只读一份多维表格。

## 先理解四道门

飞书读取不是“登录”或“加协作者”二选一。下面四项必须同时成立，并按顺序检查：

1. **应用配置**：`lark-cli` 里存在一个命名 profile，例如 `sentinel`。
2. **API 权限**：这个 profile 对应的应用具备多维表格只读 scope。
3. **用户登录**：业务本人登录到同一个 profile，取得 user 身份授权。
4. **文档权限**：第 3 步实际登录的账号是目标 Base 的协作者。

本程序固定使用 `--as user`。因此文档作者要添加的是**业务本人实际登录的飞书账号**，
不是机器人或应用。添加机器人对当前实现没有作用。

## 第 0 步：先检查链接

可直接解析的原始 Base 链接形如：

```text
https://example.feishu.cn/base/<base_token>?table=<table_id>
```

如果拿到的是下面这种分享视图链接，先停止：

```text
https://example.feishu.cn/share/base/view/shr...
```

`shr...` 是分享视图标识，不是 `base_token`。浏览器能打开分享页，不代表 API 已拿到
Base 和数据表的真实 ID。请文档作者提供原始 Base 链接，或由已能访问原表的人解析后
提供 `base_token` 与 `table_id`。不要靠反复登录解决链接类型错误。

## 第 1 步：确定唯一 profile

先查看 `followup/config/ledgers.json` 里这份飞书台账的 `profile`。后续每条
`lark-cli` 命令都必须显式带同一个名字。以下示例使用 `sentinel`。

```bash
lark-cli config show --profile sentinel
```

- 能显示 App ID：继续第 2 步。
- 报 profile 不存在或未初始化：先创建配置，**重新登录不能代替这一步**。

从零创建一个命名 profile：

```bash
lark-cli config init --name sentinel --new
```

这一步应在普通终端上下文执行，会打开飞书应用配置流程。若在 Hermes 内执行时提示
“Agent context detected”，不要强行 `--force-init` 创建一套平行应用。当前程序必须使用
user 身份；安装助手应先向用户明确说明会以她的身份读取已授权 Base，并取得同意，再按
lark-cli 的正式绑定流程执行：

```bash
lark-cli config bind --source hermes --identity user-default --profile sentinel
```

绑定可能改变 Agent 的身份策略，不得静默执行。用户不同意 user 身份授权时，应停用该
飞书数据源，不得偷偷降级为 bot；bot 看不到用户自己的文档权限。

若组织策略禁止创建或绑定应用，立即停止，请飞书管理员或
已有应用的负责人协助；不要临时换 profile，也不要把 App Secret 粘贴到聊天记录里。
复用已有应用时，App Secret 只能通过标准输入交给 `--app-secret-stdin`，不得写进命令、
配置模板、日志或 Git。

## 第 2 步：业务本人登录同一个 profile

只申请当前功能需要的多维表格只读权限，以及定时任务刷新用户令牌所需的
`offline_access`：

```bash
lark-cli auth login --profile sentinel --scope "bitable:app:readonly offline_access" --no-wait --json
```

`offline_access` 只让 lark-cli 在用户令牌到期后继续刷新已授权的只读权限，不会把
多维表格权限升级为可写。缺少它时，手工验收可能成功，但定时任务会在短期令牌到期后
失效。

安装助手应把返回的授权链接和二维码交给业务本人，由她使用**准备加入文档协作者的
同一个飞书账号**完成授权。授权完成后，由安装助手继续完成 device-code 流程。

然后核对实际登录身份：

```bash
lark-cli auth status --profile sentinel --json --verify
```

必须确认：

- `verified` 为成功；
- user 身份有效；
- scope 包含 `bitable:app:readonly` 与 `offline_access`，并存在可用的刷新期限；
- 显示的用户名正是文档作者添加为协作者的账号。

如果登录到了另一个账号，先修正账号；不要让作者把多个账号都加进去碰运气。

## 第 3 步：文档作者添加协作者

把第 2 步 `auth status` 显示的实际用户账号加入目标多维表格协作者，至少授予可查看
权限。当前程序只调用 `+table-list`、`+field-list`、`+record-list` 三个只读命令，
不需要编辑权限。

如果 Base 开启了高级权限，还要确认这个用户在高级权限中能看到目标数据表与记录；
“能打开 Base 首页”不一定代表能读目标表中的全部记录。

## 第 4 步：解析真实 ID，并做只读探针

有原始 Base URL 时：

```bash
lark-cli base +url-resolve --url "<原始 Base URL>" --profile sentinel --as user
```

把返回的 `base_token`、`table_id` 写入运行目录的
`followup/config/ledgers.json`。不要把完整 URL 当成 `base_token`。

最后只读验证：

```bash
lark-cli base +table-list --base-token "<base_token>" --profile sentinel --as user --format json
```

只有这条返回 `ok: true`，才算飞书接入完成。之后再运行项目自检：

```bash
FOLLOWUP_HOME="<运行时目录>" python3 scripts/doctor.py
```

## 报错只走一条处理路径

| 自检错误分类 | 含义 | 只做什么 |
|---|---|---|
| profile 不存在/未初始化 | 应用配置还没建 | 先 `config init`，不要先登录 |
| 用户未登录/token 失效 | 该 profile 没有有效 user token | 对**同一 profile**重新登录 |
| `missing_scope` | 应用或用户授权缺 Base API scope | 补最小只读 scope，不要让作者重复加协作者 |
| `91403`/资源权限 | 登录身份存在，但看不到目标 Base | 作者给 `auth status` 显示的账号加协作者 |
| keychain 不可用 | 定时任务读不到本机凭证存储 | 先检查 profile；再评估 keychain downgrade 的安全取舍 |
| 分享链接无法解析 | 拿到的是 `shr...`，不是 Base ID | 向作者要原始 Base 链接或真实 ID |

任何一步失败都先修当前这一层。不要同时重新登录、换 profile、添加机器人和修改链接，
否则下一次成功也无法知道究竟是哪项生效。
